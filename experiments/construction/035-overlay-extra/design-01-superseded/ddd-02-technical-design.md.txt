# Design proposto — IMP-035 / V-034 — reparação unilateral

**Só Model aprovado. Design, contratos, âmbito e minuta ADR abaixo são propostas.**
G-EXTRA-ADR permanece pendente para IMP-035; não continuar Java/Implement/Test.
Base integrada 22622c1d7eb0fdab3df684f2fac10263cff11736. Não ler/analisar código
Java nesta etapa: as APIs de base são as documentadas nas interfaces/walkthrough
aprovados. A compatibilidade efetiva será conferida na revisão ADR/Implement.

## 1. Requisito e clarificação do atendimento

Q-C-20: um nó inicia procura autónoma apenas com **zero vizinhos ACTIVE**.
O utilizador aprovou Model e esclareceu: **o destino pode estabelecer a ligação
pedida pelo isolado, preservando sessões existentes**. Não exigir que o destino
fique isolado, perca sessões ou tenha aprendido reciprocamente o requerente.

Conservar o menor nodeId como iniciador do TCP persistente. Atender significa
validar/admitir o pedido e completar a sessão: se o destino é o menor ID, ele
faz o dial de retorno; se é o maior, confirma o pedido e recebe o HELLO na
conexão iniciada pelo isolado. Não introduzir exceção silenciosa à ADR-019.
Ambos os casos resultam numa única sessão persistente e mesmo codec/listener.

Cenário A: S–R1/R2–C; morte de R1 conserva alternativa R2, sem aresta nova;
morte de R2 isola S/C e permite S–C. Cenário B: S–R1–R2/R3–C; morte de R2
conserva R3, sem procura; morte de R3 isola C. R1 admite C, conservando S–R1
com o mesmo connectionId. Os candidatos e autorizações são aprendidos antes
das falhas. Não consultar bootstrap novamente, reiniciar sobreviventes ou
apresentar conectividade de controlo como vídeo. Falha silenciosa/UDP-only
não ganha deteção nova; morte abrupta com EOF/RST é ensaiável neste incremento.

## 2. Porquê uma autorização prévia emitida pelo destino

O contrato integrado divulga endpoints e proveniência do anunciante. Isso
permite ao isolado localizar o destino, mas não permite ao destino verificar
uma introdução unilateral se não tiver cache recíproca. Aceitar só a afirmação
«R2 anunciou-te» autorizaria qualquer ID/endereço que inventasse essa frase.

Proposta: cada nó emite aos vizinhos ACTIVE **permissões opacas de introdução**.
O vizinho pode anexar a permissão aos anúncios desse nó para os seus próprios
vizinhos. O destino guarda o registo limitado das permissões que emitiu e pode
validá-las depois da morte do anunciante, sem procurar o anunciante/bootstrap.

Exemplo: R1 emite uma permissão a R2 na sessão R1–R2. R2 anuncia R1 e essa
permissão a C. Quando R2/R3 morrem, C apresenta a permissão a R1. R1 valida o
seu próprio registo, identidade/endpoint de C e contexto; não precisa de ter
uma entrada C na cache. Uma cache de endpoints sem permissão pode continuar a
servir a descoberta, mas não autoriza reparação: estado explícito NO_PERMISSION.
Isso não desativa descoberta ou cria modo base; a função aguarda autorização.

Não é autenticação criptográfica. A permissão é transferível por vizinho direto
no laboratório confiável da ADR-021; o destino valida emissão/proveniência,
não prova criptograficamente a honestidade de C/R2 nem que C está isolado.
Um nó malicioso ou um token copiado fora da regra exigiria outra política de
segurança. Não usar IP remoto como identidade, assinaturas inventadas ou DB.

## 3. Registos imutáveis e APIs propostas

Nomes e assinaturas abaixo são propostas a conferir na revisão ADR, sem código
Java lido/alterado. Usar records, enums de códigos explícitos e cópias defensivas.

- protocol/RepairMessage.java: sealed Payload com Grant, Intent, Result e Bind.
  Grant contém contexto HELLO, destinatário/instância, permitId, grantGeneration positiva e validForMillis.
  Intent contém destinatário/instância, Endpoint do requerente e prova
  (permitId, grantHelloId, introducerId, introducerInstance).
  Result contém destinatário/instância, relatedType, disposição, motivo e
  admissionId. Bind contém destinatário/instância, intentId, admissionId e
  Endpoint do iniciador permitido. requestId é sempre o intentId nos tipos
  21/22/23; o HELLO posterior tem o seu requestId próprio, atual e não zero.
- DiscoveryMessage.Snapshot conserva directNeighbors(): List<Endpoint> e ganha
  permits(): List<Optional<PermitRef>>, com cardinalidade igual/cópia defensiva.
  PermitRef(permitId, grantHelloId) é imutável. Construtor Java anterior cria
  Optional.empty para cada endpoint; não aceita o formato binário anterior.
- CandidateCache.Provenance ganha Optional<PermitRef>; conservar construtor
  anterior por overload com Optional.empty. SourceKey/geração/queryStarted/TTL
  conservam significado; issuerInstance vem do Endpoint e introducerId/instance
  da proveniência da sessão do anúncio. Nunca fabricar prova ao ler cache.
- OverlayRecovery é componente confinado ao SerialOwner do nó. Contrato interno
  conceptual: onNeighborUp/Down(Session), onGrant(Session, Grant, observedAt),
  onIntent(Channel, ControlMessage, observedAt), onResult/onBind, maintain(now),
  onCandidateSnapshot(...), requestClose(remainingBudget), snapshot(). Não criar
  executor, writer, listener ou rede em OverlayRecovery.
- NeighborManager continua a possuir Context/Attempt/Peer e os mecanismos de
  dial/DNS/HELLO/flush; recebe o modo do dial (configurado, intenção ou retorno)
  e emite callbacks correlacionados a Recovery. Não copiar o transporte.
- OverlayNode.recoveryStatus(): RecoveryStatus devolve snapshot publicado
  imutável; também manter candidates/snapshot/discoveryStatus anteriores.
  RecoveryStatus: fase/motivo, ACTIVE count, candidato opcional e retry relativo,
  sem nonce/token/payload ou histórico. Fases ISOLATED/WAITING/REQUESTING/
  ADMITTING/ACTIVE/STOPPING e razões finitas, não enums wire.
- Connection.terminated(): CompletionStage<Void> novo/aditivo, mínimo e só
  completado depois dos dois workers e libertação física da reserva. Conclusão
  fora dos locks. Não significa connectionClosed nem fecho lógico. Preservar
  send/sendAndFlush/close e comparar connectionId/instanceId no callback.
- CLI mantém neighbors/quit/--help e ganha recovery: uma linha de estado e até
  oito candidatos/motivos, sem tokens. Informação útil sobre isolamento/retry,
  sem imprimir mapas, cache completa ou detalhes internos sem limite.

## 4. Permissões, TTL e cache

1. Em sessão ACTIVE, o emissor pode enviar REPAIR_GRANT ao vizinho. Cada emissão
   tem nonce UUID não zero e único na execução; lookup usa (issuerInstance,
   permitId). GrantGeneration cresce por sessão, 1..Long.MAX_VALUE sem wrap; só avança
   após enqueue aceite. O registo guarda vizinho id/instance/HELLO e endpoint/execução do
   próprio emissor. Não usar contador que faça wrap ou reutilizar nonce ativo.
2. ValidForMillis wire é exatamente 120000; expiração **no emissor** desde a
   admissão da GRANT na fila comum, medida em relógio monotónico local. Permissão
   expirada não é válida mesmo se um future de escrita concluir tarde.
3. Registry local: até 256 permissões, com até quatro por sessão emissora. Sem
   espaço, não emitir/evictar uma permissão viva para fingir continuidade; motivo
   PERMISSION_CAPACITY. Expirar no tick comum, sem timer por permissão.
4. Renovação elegível a cada 30 s/sessão; seleção round-robin, saída de GRANT
   <=4/s global, sem fila de mensagens à espera. A nonce só entra no registry
   após admissão atómica de envio; falha de envio/prazo retira a emissão lógica,
   conservando recursos físicos até terminarem. Não revogar permissões válidas
   já entregues só por fechar a sessão do anunciante; continuam até 120 s.
5. O vizinho conserva só a última GRANT válida por sessão (<=63). Verifica o
   HELLO/identidade/destinatário atuais e geração estritamente crescente; duplicata
   ou geração/token antigos não substituem/renovam a prova nem o prazo de 30 s.
   Só a divulga durante os primeiros 30 s locais desde a receção, em snapshots
   de adjacências ACTIVE. Ausência/atraso de GRANT produz prova ausente, sem
   fingir incapacidade do peer ou fechar o controlo.
6. Não há relógios sincronizados nem TTL absoluto remoto. Uma GRANT atrasada
   pode já estar inválida no emissor; o lookup final deste é autoritativo.
   120/30 s dão margem ao TTL de cache 60 s em condições normais, sem prometer
   disponibilidade para mensagens arbitrariamente atrasadas ou fila saturada.
7. Em R2, o snapshot de R1 contém endpoint atual de R1 e PermitRef obtida na
   sessão R1–R2. C guarda-a no mesmo claim (R2, instância, conexão, HELLO,
   geração, queryStarted). Não são anunciadas entradas da cache como adjacências.
   Campo ausente, inválido ou prova expirada não prolonga o claim.
8. Cache conserva 128 IDs x quatro fontes e TTL 60 s desde QUERY admitida. Apenas
   snapshot corrente e geração crescente pode substituir prova/renovar claim.
   D07e continua: token/queryId/geração antigos não alteram cache, query,
   watermark, TTL ou sessão. Fechar R2 não apaga a prova retida por C nem o
   registry de R1 que ainda permite verificá-la.
9. Sessão reparada já confirmada vive independentemente do TTL/GRANT. Antes de
   novo commit, revalidar claim na origem e permissão no destino; expiração ou
   conflito invalida pendente, não fecha sessão saudável. Reiniciar o emissor
   muda instanceId e perde registry, invalidando permissões antigas.

## 5. Contrato TCP v2 proposto e comprimentos

**Delta de contrato, não mera configuração.** Um codec/envelope TCP version=2,
framing u32/body 37..65536, UTF-8 estrito, código 3 rejeitado. Não mudar bootstrap, framing/envelope, códigos existentes ou UDP.
Os formatos HELLO/HELLO_OK conservam largura, com nova máscara obrigatória abaixo. Tipos novos explícitos: 20 REPAIR_GRANT,
21 REPAIR_INTENT, 22 REPAIR_RESULT, 23 REPAIR_BIND. Total proposto: 22 tipos
ativos (1,2,4..23), em vez dos 18 do contrato integrado. Nenhum runtime antigo,
negociação com JAR antigo ou fallback; todos executam o mesmo JAR revisto.
HELLO/ACK passam a supported=required=selected=3: DISCOVERY=bit0 (1) e
REPAIR=bit1 (2), ambos obrigatórios e bits restantes zero. Não negociar um
subconjunto nem admitir um peer só DISCOVERY. Isto altera os valores de máscara
dos tipos5/6 da ADR-034 e precisa de aprovação explícita da revisão; os tamanhos
HELLO72..386/ACK41..72 permanecem. Incompatibilidade rejeita apenas a tentativa,
sem fallback ou efeito global. Todos os nós da mesma versão do JAR exigem ambos.

SNAPSHOT (19) mantém cabeçalho, contexto/geração/count e Endpoint; **após cada
Endpoint** acrescenta u8 hasPermit (0/1) e, se 1, UUID permitId + UUID grantHelloId.
Não autodetetar ou tentar descodificar o formato anterior. O construtor anterior
é compatibilidade Java, não runtime wire. Sem entradas, bytes do snapshot ficam
iguais; com entradas mudam explicitamente e precisam de fixtures independentes.

Todos os inteiros usam big-endian. String é u16 + UTF-8; IDs 1..32, host 1..253;
UUID de execução/token/admissão/pedido não zero. Endpoint conserva formato.
Envelope comum: 36+s bytes; Endpoint: 25+n+h; s/n/r/i são bytes de nodeId e h host.

| Tipo | Campos de payload na ordem wire | Corpo mínimo..máximo |
|---|---|---:|
| 20 GRANT | helloId UUID, recipientId string, recipientInstance UUID, permitId UUID, grantGeneration u64 positiva <=Long.MAX_VALUE, validForMillis u32=120000 | 100..162 |
| 21 INTENT | recipientId string, recipientInstance UUID, requester Endpoint, permitId UUID, grantHelloId UUID, introducerId string, introducerInstance UUID | 134..510 |
| 22 RESULT | recipientId string, recipientInstance UUID, relatedType u8 (21/23), disposition u8, reason u8, admissionId UUID | 75..137 |
| 23 BIND | recipientId string, recipientInstance UUID, intentId UUID, admissionId UUID, initiator Endpoint | 115..460 |
| 19 SNAPSHOT revisto | campos existentes + por endpoint hasPermit e dois UUIDs quando 1 | 82..21753 |

RESULT dispositions: DIRECT=0, REVERSE=1, ACK_REVERSE=2, REJECT=3.
Reasons: OK=0, NO_PERMISSION=1, EXPIRED=2, BAD_PROVENANCE=3, BUSY=4,
ALREADY_ACTIVE=5, IN_PROGRESS=6, NO_NEED=7, IDENTITY=8. Códigos explícitos;
DIRECT/REVERSE/ACK usam OK e admissionId não zero; REJECT usa reason !=OK e
admissionId zero. DIRECT/REVERSE/ACK têm relatedType=21; resposta ao BIND usa
DIRECT/REJECT com relatedType=23. BIND.intentId deve igualar o requestId.
HELLO posterior usa novo ID; admissionId não substitui a correlação do HELLO.

Cap extra 32768 aplica-se antes de alocar a 18..23; máximo SNAPSHOT 21753 ainda
cabe. Count <=63 verificado antes da lista, hasPermit só 0/1, UUIDs/bytes finais
validados atomicamente. Snapshot sem prova continua aprendizagem, sem autorização
reparadora. GRANT não altera cache/geração/query nem é anúncio de candidato.

## 6. Pedido, atendimento e iniciador

### 6.1. Pedido inicial

Isolado A seleciona B/claim com PermitRef válida localmente. Abre um canal
**provisório de controlo na controlPort de B**, usando o mesmo Transport, codec,
FIFO/writer/caps. Envia INTENT em vez de HELLO automático. Não abre dataPort,
listener/codec auxiliar nem segunda sessão persistente. O canal conta em C e
nos limites de pré-handshake; não produz NeighborUp ou adjacência anunciável.

B valida versão/tipo/identidade/endpoint, destinatário e a sua própria instância;
faz lookup do nonce e confere grantHelloId/introducer id/instance, validade e
limites. Só depois reserva admissão para (A,B), admissionId e Context próprio.
A intenção não altera o grafo bootstrap. B não precisa de cache A ou isolamento.
Antes da validação não cria Peer/status por ID desconhecido; apenas contexto
físico limitado e diagnóstico genérico com throttling.

### 6.2. A é o menor ID: promoção do mesmo canal

B responde RESULT DIRECT e conclui write/flush. A recebe/valida, confirma que
continua isolado e que o claim não expirou/conflitou, e envia HELLO v2 normal
nesse canal. B só aceita esse HELLO para o par/endpoint/execução da admissão
local do Context; não uma exceção global ao grafo. HELLO_OK e barreiras de
flush existentes completam uma sessão. O canal provisório torna-se persistente,
sem segundo dial. B preserva as outras sessões.

### 6.3. A é o maior ID: o destino B estabelece a ligação

B responde RESULT REVERSE com admissionId. **A instala a espera de retorno
antes de enviar RESULT ACK_REVERSE**, com os mesmos intentId/admissionId.
B só programa retorno após receber esse ACK válido; flush local do REVERSE não
prova receção remota. ACK não produz ACK de ACK.

O canal de intenção é fechado após o ACK; B aguarda Connection.terminated()
local e só então resolve/diala o endpoint de A. A mantém apenas a espera
limitada e o seu listener de controlo já existente. Nenhuma thread/slot do
canal antigo é reutilizado por ter terminado apenas o future lógico.

No retorno, B envia BIND com intentId/admissionId e o seu Endpoint. A valida
contra a espera atual/instanceId/endpoint B aprendido, isolamento e claim ainda
válido. A responde RESULT DIRECT relatedType=23 no mesmo canal. B então envia
HELLO v2 normal, sendo o menor nodeId. Ambas as pontas usam a admissão efémera
para autorizar fora do grafo. Completar handshake/flush e só depois NeighborUp.

A agenda de retorno não apaga sessões saudáveis de B. Se A entretanto ganha
vizinho configurado, cancela a espera e rejeita BIND NO_NEED; não aceita uma
segunda aresta por um isolamento já satisfeito. Canal antigo ainda fisicamente
cobrado ou falta de recurso pode levar a BUSY/retry, sem violar C.

```mermaid
sequenceDiagram
    participant A as Isolado A (ID maior)
    participant B as Destino B (ID menor, saudável)
    A->>B: INTENT + permissão aprendida antes da falha
    B-->>A: RESULT REVERSE + admissionId
    Note over A: Instalar espera correlacionada
    A->>B: ACK_REVERSE
    Note over A,B: Fechar canal provisório; B espera terminação física local
    B->>A: Dial de retorno + BIND
    A-->>B: RESULT DIRECT (BIND)
    B->>A: HELLO v2
    A-->>B: HELLO_OK v2 e flush
    Note over A,B: Uma sessão ACTIVE; sessões saudáveis de B preservadas
```

## 7. Seleção, concorrência, limites e prazos

- Trigger: consulta inicial terminada e zero ACTIVE. Cache começa vazia; não há
  reparação sem aprendizagem prévia. READY sem vizinhos publica ISOLATED.
  Não esperar que todos os candidatos/configurados tenham falhado para observar
  isolamento, mas coordenar reservas com os retries configurados existentes.
- Uma tentativa autónoma lógica por nó, uma por par; até duas admissões recebidas
  (também quando saudável). Tabelas dinâmicas até min(16,C) pares; tabela
  configurada mantém <=63. Grau ACTIVE total <=min(C,63). São limites distintos,
  não somar os mapas para permitir mais sockets. Todas as reservas físicas <=C.
- Recusa de unknown/invalid INTENT não cria entrada dinâmica. Entrada dinâmica
  terminal sem sessão sai quando terminam recursos; rejeições não deixam mapa
  ilimitado de desconhecidos. Status/cooldown candidatos limita-se aos 128 IDs
  presentes na cache; nunca 128 timers/dials. Registry/GRANT usam os limites da §4.
- Sort por nodeId e SourceKey estável, round-robin entre candidatos/até quatro
  claims. Não marcar candidato inteiro indisponível por falhar uma de várias
  provas. Sem RTT/custo ou preferência por SERVER; não são rotas/streams.
- Backoff por candidato usa overlay.retry.initial/max/jitter já existentes
  (defaults 500/5000 ms e 10%), limitado pelo teto com aritmética verificada.
  Não inventar o teto de 30 s: essa pausa pertence à descoberta. Uma ronda
  esgotada espera o menor prazo elegível; sem candidatos só reagir ao tick/evento,
  sem socket, DNS ou fila de tentativas armazenadas.
- Uma admissão por par; simultâneos A→B e B→A convergem para a intenção cujo
  requerente é o menor ID. Retirar logicamente a oposta, aguardar terminação
  física e não substituir sessão ACTIVE. Duplicata do mesmo requerente recebe
  IN_PROGRESS, sem reeleger por UUID/ordem acidental ou renovar prazo.
- Distinguir necessidade local de intenção recebida: um NeighborUp satisfaz a
  necessidade local e cancela commits autónomos obsoletos. Não cancelar pedido
  remoto só porque o destino tem S ACTIVE; esse é precisamente o cenário B.
- Operação total de reparação <=15 s locais desde a seleção/receção inicial;
  cada lado tem o seu prazo e nunca o renova por resposta duplicada. Origem
  limita também ao TTL restante do claim; destino, à GRANT/admissão. Subfases
  INTENT/RESULT/ACK/BIND: <=2 s; DNS/bind e dial usam control.connectTimeout
  separadamente; HELLO usa overlay.helloTimeout, sempre min com o restante.
  O teto de 15 s é orçamento de operação proposto, não SLA de recuperação.
- Revalidar necessidade/claim/prova/recurso em cada commit. Primeira confirmação
  ACTIVE fecha a necessidade. Uma configuração que recupera primeiro vence
  antes do commit da reparação; nenhum callback antigo remove sessão já válida.
- Todos os extras 18..23 usam admissão da FIFO comum: Q>=2, duas posições livres,
  no máximo um extra enfileirado (incluindo take→inFlight), um em escrita por
  ligação, quatro tickets físicos globais. BACKPRESSURED adia/falha só a operação;
  não fecha sessão saudável nem cria fila extra. Tipos normais não podem ser
  usados para contornar a quota. GRANT/INTENT/RESULT/BIND têm o mesmo tratamento.
- Usar o tick 100 ms coalescido já existente, chamado também para Recovery no
  mesmo owner. Registry expirado, estados e deadlines lógicos não ganham jobs
  por entrada. Não criar outro pool/timer/listener. Resolver/dials continuam a
  contar até terminação física, mesmo depois de cancelar future lógico.

## 8. Identidade, erros e callbacks antigos

Antes de recuperar conteúdo, validar handle/execução/identidades/estado. Em
ACTIVE, GRANT completa com token HELLO antigo é descarte STALE sem Down ou
alterar prova corrente. Snapshot preserva exatamente D07e: geração/token antigos
não terminam consulta nem impõem cooldown. GRANT inválida atual completa pode
ser descartada com diagnóstico limitado sem fechar controlo saudável. Snapshot
com permit flag/nonce inválido é rejeitado atomicamente, sem aprendizagem parcial.

readFrame.RejectedExtraContent é ampliado ao tipo20, cujo prefixo HELLO/recipient
é o mesmo formato já legível. GRANT rejeitada vai para Recovery, nunca para
a regra que falha uma QUERY de Discovery. Tipos21..23 não têm recuperação de
conteúdo fora da sua máquina de tentativa.

Nos canais provisórios, frame sem contexto, intenção/nonce/instância inválida,
comprimento/truncamento/UTF-8 de identidade ilegível é terminal **nessa tentativa**.
Rejeição semântica segura pode produzir RESULT REJECT após flush e fechar;
se framing/envelope inseguros, só fechar. ERROR recebido não recebe ERROR nem
RESULT de resposta. Conteúdo inválido num canal provisório não é autorização
para continuar a receber HELLO. Resultados/replays fora do intentId/admissionId/
connectionId/instanceId correntes não mudam a admissão nova.

Prazo/cancelamento remove elegibilidade, não marca workers terminados. Conclusão
de escrita/terminated publica evento curto fora de locks; owner compara Context,
Attempt e epoch local da necessidade. Nunca uma callback antiga fecha o handle
novo. Guardar apenas IDs/enums/escalares limitados para diagnóstico, sem pacote
inteiro inválido ou exception textual na rede. JAR antigo não é cenário suportado.

## 9. Shutdown e isolamento de falhas

requestShutdown/recovery.requestClose bloqueiam novas permissões/intenção/dials,
cancelam necessidade/admissões lógicas e limpam registry/cache auxiliar limitada.
Usar prazo global restante do nó; não acrescentar 15 s ao shutdown de 3 s.
Sessões ACTIVE mantêm NODE_LEAVE/write/flush e o mecanismo anterior; canais
provisórios terminam localmente com cleanup limitado. Callbacks nunca esperam
sendAndFlush/terminated/joins no owner. A reserva só sai na terminação física.

Worker preso produz timeout explícito e continua cobrado, sem alegar shutdown
completo. Peer inválido, indisponível, sem permissão ou sem slot não provoca
FAILED global/fim da CLI nem fecha S–R1. Saturação crítica de owner conserva a
semântica operacional já aceite; não transformar falha de infra em sucesso.

## 10. Âmbito proposto e compatibilidade

[Proposta de ampliação de oito para 30 caminhos](scope-change-proposal.md).
É necessária para GRANT, prova no SNAPSHOT, INTENT/RESULT/BIND, codec comum,
cache e observação de terminação física. **Não está aprovada pelo início de Design.**
Não alterar catálogo/ADD para aparentar autorização: os oito caminhos continuam
normativos até revisão de âmbito/ADR. Nenhum Java/recurso/POM foi alterado.

Preservar bytes de REGISTER/bootstrap/UDP e restantes payloads. Há dois deltas
explícitos: máscara obrigatória dos tipos5/6 e prova do SNAPSHOT19. Sete vetores
precisam de migração: tcp-hello, tcp-hello-ok, tcp-invalid-capability-not-required,
tcp-invalid-capability-reserved e tcp-discovery-snapshot, tcp-snapshot-duplicate,
tcp-snapshot-invalid-role. Os outros43 TCP e16 UDP ficam byte a byte.
Nas máscaras, positivos1→3; negativo not-required usa supported3/required0 e
reserved usa supported7/required3 para continuar a atingir bit reservado, não
apenas ausência de REPAIR. Missing0/0 permanece negativo byte a byte. Nos três
snapshots, continuar sucesso/duplicação/role inválido, não EOF mascarado.
Os 18 tipos integrados mantêm códigos; somam-se quatro tipos, sem reutilizar 3.

Propor 24 fixtures novas independentes (10 positivas/14 negativas), total alvo
90=50 TCP (sete migradas)+24 TCP novas+16 UDP. Nenhuma fixture criada por este Design.
As positivas cobrem GRANT min/max, INTENT min/max, quatro dispositions RESULT
com contexto válido e BIND min/max. Negativas: nonce/HELLO zero, validade fora
de 120000, capacidade só DISCOVERY, tipo relacionado inválido, códigos/disposition
ou reason incompatíveis, ACK fora de contexto, BIND intentId divergente,
truncamento, flag de prova inválida, prova truncada e comprimento extra fora cap.
Oráculos de contexto/estado podem usar wire válido e rejeição pelo owner, não
rotular erro de sessão como erro do decoder. V-ADD verifica bytes/referências,
Java compara encoder/decoder com vetores sem produzir o esperado por si.

Os testes V-033 migram payloads com Optional.empty por omissão e acrescentam
provas; cache/TTL/D07e/FIFO/flush/identidade mantêm oráculos. Os cenários que
provavam «IMP-034 não repara» passam a usar aprendizagem isolada por componente;
a aplicação normal agora repara obrigatoriamente ao isolar. Não criar flag off
para manter testes verdes nem apagar testes. Testes de bootstrap negativos
passam a percorrer os quatro tipos novos, sem introduzir bootstrap de reparação.

## 11. Injeções e oráculos D01–D24 / M01–M18

Injetar clock monotónico, fonte de nonce/intent/admission determinística,
resolver/transport adapter, writer/flush/terminated e SerialOwner manual pelos
pontos de teste documentados de NeighborManager/Transport. Recovery recebe essas
portas, não cria sockets em testes lógicos. Nonces fake não são configuração.
Fake physical worker segura a reserva após cancelamento e até sinal explícito;
clock falso avança prazos sem sleeps. Repetir trajetos de promoção/retorno com TCP
real, não substituir entrega/flush por future simulado no oráculo de rede.

## 13. Minuta de decisão para futura ADR-035 — Proposta

Não é revisão ADR concluída nem nova ADR Aceite. Na etapa ADR, propor substituição
parcial de ADR-033/034/019: admissão de arestas por permissão emitida pelo destino,
prova no snapshot19, quatro tipos novos v2 e máscaras obrigatórias3 em HELLO/ACK,
canal provisório no mesmo listener,
retorno pelo menor nodeId e observação aditiva de terminação física. Conservar
cache/TTL/proveniência, isolamento/recursos e UDP. Substituição não alarga caps
nem altera bootstrap/UDP; os tipos5/6 mudam apenas a máscara obrigatória. Atualizar secções6/8/interfaces, testes e
catálogo só quando âmbito/contrato forem revistos e aprovados.

Alternativas rejeitadas nesta proposta: confiar só em endpoint autoafirmado;
exigir cache recíproca (não suporta M05); ambos dialarem sessão persistente;
maior ID persistente sem exceção aprovada; catálogo/bootstrap de reparação;
canal/dataPort separado; HMAC/PKI novas sem necessidade do laboratório; tratar
cancelamento como terminação; desativar extra/Q1 para evitar quotas.

**Decisões novas para revisão (Q-C-21):** permissão transferível e seus prazos/
caps, alteração de SNAPSHOT19, máscaras3 e22 tipos, troca provisória/promoção/retorno/ACK,
limites de admissão e teto15 s, Connection.terminated e âmbito30. A clarificação
humana de atendimento já está aceite; não se presume aprovação destes detalhes.

Parar em Design para revisão antes de ADR/Implement/Test. Sem commits/push.

## 14. Contratos de integração propostos (documentação)

Assinaturas para revisão; não representam interfaces já implementadas:

```java
OverlayRecovery(NodeConfiguration config, UUID instanceId, LongSupplier clock,
                Entropy entropy, RecoveryPorts ports);
void onNeighborUp(Neighbor.Session session);
void onNeighborDown(Neighbor.Session session);
void onFrame(ChannelLease channel, ControlMessage message, long observedAt);
void onRejected(ChannelLease channel, MessageCodec.RejectedExtraContent rejected);
void maintain(long now);
void requestClose(long remainingNanos);
RecoveryStatus snapshot();

interface Entropy { UUID nextId(); }
interface RecoveryPorts {
    Map<String, Neighbor.Session> active();
    List<CandidateCache.CandidateView> candidates(long now);
    boolean post(Runnable event);
    DialLease dial(AttemptKey attempt, ControlMessage.Endpoint endpoint, long remainingNanos);
    Connection.ExtensionEnqueue sendExtra(ChannelLease channel, ControlMessage message);
    void close(ChannelLease channel);
    void publish(RecoveryStatus status);
}
record AttemptKey(UUID instanceId, UUID intentId, long needEpoch, String targetId) {}
record DialLease(CompletionStage<ChannelLease> connected, CompletionStage<Void> terminated) {}
record ChannelLease(UUID connectionId, CompletionStage<Void> terminated) {}
```

As portas acedem pelo owner; connected dá resultado lógico, terminated só fim
físico, incluindo resolver/dial nativos ainda vivos e Connection.terminated
quando houve socket. Handles reais ficam no adapter NeighborManager; lease não permite que
Recovery escreva diretamente no socket. As stages publicadas são mínimas;
cancelar uma cópia não cancela arbitrariamente recursos do nó. NeedEpoch é
contador local monotónico sem wrap; ao esgotar recusar necessidade nova com
motivo explícito, sem reciclar correlação. snapshot é valor imutável publicado,
não um mapa vivo. APIs públicas anteriores conservam comportamento documentado.
